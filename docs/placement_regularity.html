Pyrope placement regularity

Small source programs generate approximately 10K–100K standard cells around repeated fake hard macros. The purpose is to make physical structure easy to inspect through the complete Pyrope → graph → ABC mapping → fp_plan → macro_plan → final detailed placement → OpenTimer flow.

The expected PNGs below are topology sketches, with macro squares and standard-cell corridors. Actual PNGs and timing numbers are generated locally under ignored repros/placement_regularity/. No measured result is checked into this guide. Tile colors are consistent between the sketches and stage views; outlines identify macro bodies, with red marking the four explicit corner anchors in the serpentine. A sketch does not prescribe an exact gate location.

What is measured

MetricInterpretation
HPWL (µm)Unweighted placed net half-perimeter sum reported by the flow, including its physical nets.
WNS / TNS (ns)OpenTimer setup slack with a 20ns clock and the invented Liberty plus LEF RC. TNS sums negative slack; positive WNS is possible. These are placement RC estimates, without routing or clock-tree synthesis.
Pattern RMS (pitches)Macro centers fit to the expected template with translation, uniform scale, arbitrary rotation, and reflection. Zero means the illustrated regular frame; lower is better. Macro centers suffice because all macros are equal squares.
Normalized edge length CVFor each neighbor edge, divide its measured length by its length in the template, then take standard deviation divided by mean. Zero means equal pitch, including the longer hierarchical links.
Legal / GP convergedReported separately. Legalization must succeed, even when GP exhausts its iteration budget.

Flow completion, a legal final DEF, expected macro count, 10K–110K standard cells, and finite HPWL/WNS/TNS are required. Pattern scores are reported for visual review; only an explicit --max-pattern-rms turns them into a pass/fail condition. No exact coordinate golden is imposed on the heuristic placer.

The deliberately fake technology

Liberty and LEF contain INV, BUF, NAND2, NOR2, XOR2, DFF, TIE0 and TIE1, one drive strength each. A 40×40µm BLOCK macro has 32 independent feed-through lanes with 0.4ns arcs. Standard combinational arcs are 0.05ns, flop clock-to-Q is 0.05ns, and setup/hold are 0.02ns. Rows are 2µm high with 1µm sites; DBU is 1000/µm. Two orthogonal routing layers supply explicit fake RC. These values are invented; they are not Sky130 characterization.

Only the hard-macro interface is Verilog. The designs, connections, hierarchy and surrounding logic are Pyrope, using import("lg:REG_MACRO"). Each tile has 32 resetless state bits and repeated nonlinear mixing, and every tile is observable at a top output. Sequential feedback breaks the mesh/ring cycles. The explicit mapping recipe strash; &get -n; &nf; &put avoids expensive synthesis searches. Resizing, placement-driven remapping and additional timing-driven placement rounds are explicitly disabled to keep netlist identity and stage images comparable. Final STA remains enabled. Existing flow defaults are unchanged.

The run target sets synth.place.fp.min_macros=0 (flag --min-macros, default 0 here; the flow default is 2). A hierarchy candidate needs more than that many movable macros, so with the flow default these one- and few-macro tiles would never become hierarchy candidates: they would fall back to unsnapped color centroids and the floorplan snap would not be exercised. With 0, every repeated tile (four or more siblings under one parent, synth.place.fp.min_copies) is a snap-eligible hierarchy candidate. Snapshots are required: missing stage data fails the run. The optional --snap-mode alignment|symmetry sets synth.place.macro.snap_mode for the macro stage.

The mesh and hierarchy cases start with all macros movable. The serpentine imports a generated DEF containing only its four corner macros as FIXED components; all 28 other macros and all standard cells remain movable. The runner verifies each fixed corner survives unchanged and that the macro-stage handoff preserves every macro. Pyrope fixed-coordinate attributes are not consumed by the current physical flow; this fixture uses the supported DEF interface.

The serpentine explicitly selects pass.color.synth.mode=synth to keep its root logic in one color and retain the source instance names used by its DEF. The default cone coloring can wrap those instances in generated hierarchy. The other cases retain their default synthesis coloring.

The serpentine follows the alternating runs in the supplied zigzag reference, with an outside connection closing its two ends into one cycle. The reference image is not copied into the repository.

Hierarchical placement hints

Experimental implementation: pass FILE.json. Use the existing hierarchy_4x4 fixture and its invented technology with optional metadata. Keep the source, mapped netlist, connectivity, technology, seed and optimization settings identical with and without hints. The floorplanner still chooses the legal placement; a human or agent supplies relative physical intent or optional coordinate hints. Relative hints are preferred for portability.

Every hint is advisory. Missing, contradictory or unsuitable metadata must not change the circuit or override physical legality. The placer may relax or ignore a hint, report the reason, and continue ordinary placement. Bad hints may worsen QoR. This does not guarantee that an independently infeasible floorplan can be legalized. No required-placement mode is proposed here.

Current implementation

Relative hints guide FP and macro GP through soft center pulls (default per-hint weight: 0.35, valid range (0,1]), refreshed every 25 GP iterations. They add no nets, pins or timing arcs. Coordinate hints seed movable hard macros; normal placement, legal halo spacing, track alignment and legalization still apply. Final cell placement inherits the resulting macro frame and does not reapply hints.

work/synth/place/metadata.json preserves authored records and adds livehd.placement.hint_results and livehd.placement.state. Results report binding, rejected seeds, and geometric residuals after legalization. Accepted means consumed; a relationship outside one placement pitch is reported as relaxed. Clustering is an objective with no binary satisfaction threshold. Coordinate seeds are allowed to move after initialization.

Generated state uses the same position payload inside module templates. It is not automatically promoted over authored relative intent (automatic_reuse:false). Existing dependency-checked caches still own incremental reuse. The completed-placement cache hashes selected placement hints, not the filename or unrelated records, and merges generated records into the current input on restore. The inner block cache is bypassed for hint runs; synthesis and timing caches remain independent. The experimental macro=h2d solver ignores placement hints with a warning. Rigid macro magnet contraction does not yet support relative hints: those hints are discarded with a warning. Source HDL attribute lowering and migration of legacy JSON report/cache formats remain planned work; this does not silently reinterpret those existing files.

Example metadata vocabulary

The file is an array of typed records, extending the existing inou.attr convention. The explicit "class": "livehd.placement.hints" identifies this entry to the placement reader, regardless of filename or neighboring records. Each record has its own schema_version, id and design scope. A file can contain placement hints, synthesis metadata, incremental state and reports without mixing their fields. See the JSON audit and shared-format plan.

The JSON placement consumer supports the examples below for hard macros. Paths are relative to the template's instance; module selectors identify logical source definitions in this example. Exact module names are preferred; a short module name is accepted only when it identifies one definition. Ambiguous or missing instance names produce warnings. Logical memories expanded into multiple physical SRAMs must name those physical children explicitly.

HintProposed meaning
clusterPrefer a compact group. Members remain movable; its bounding box is not a physical obstacle or reserved empty rectangle.
directionPrefer the subject's body or group envelope beyond the specified side of the other body/envelope, including applicable clearance. North/south/east/west use the global floorplan axes, including inside templates.
snapPrefer neighboring facing edges with the legal halo/channel spacing and overlapping orthogonal spans. If side is omitted, let placement choose among the four sides. Snap alone does not require equal orthogonal centers or force a permanent rigid merge; abandon an incompatible adjacency.
alignPrefer equal x or y center coordinates, or an explicitly named edge. Equal x means a column; equal y means a row. A common two-dimensional cluster centroid is an attraction target, never an instruction to overlap bodies.

Optional coordinates, including incremental warm starts

Coordinate seeds are supported, although relative hints are preferred. For example, add this hint to the top template:

{
  "id": "g0-memory-start",
  "kind": "position",
  "subject": ["g0", "t0", "macro"],
  "frame": "floorplan",
  "anchor": "lower_left",
  "x_um": 120,
  "y_um": 80,
  "orientation": "N"
}

The subject is an instance path relative to the containing template; segment arrays avoid ambiguity in names containing separators. The string paths in the relative examples are readable shorthand. Coordinates use microns in the same global coordinate system as DEF, with its coordinate origin (not an implicit core-origin offset). The anchor is the lower-left corner of the oriented physical body, before halo padding. An omitted orientation retains the current legal orientation. The first implementation should target individual physical objects; a logical memory split into several SRAMs needs a group transform rather than assigning the same coordinates to every member.

This is a preferred initial position, never FIXED. GP and legalization may move the object. If the hint cannot be used because of overlap, core bounds, row/site restrictions, illegal orientation, ambiguous identity or incompatible metadata, discard the affected hint and continue normal placement. Conflicting coordinate hints have no file-order priority. Check them together against fixed geometry and other accepted hints; temporary ordinary GP overlap is not itself a reason to reject all warm-start coordinates.

Emit a warning through the normal LiveHD diagnostic sink, respecting --diag-fmt, rather than printing an ad-hoc message. Include the record and hint IDs, resolved instance, requested coordinates and rejection reason. Warn once per rejected hint/reason, not on every GP iteration. Normal movement of a successfully accepted initial guess does not produce a warning. Never fail an otherwise feasible placement solely because an advisory coordinate cannot be honored.

Source attributes and external metadata

A memory declaration (including a Verilog register declaration that infers RAM) can carry the same logical relationships as attributes. Both frontends should lower to one hint representation. Syntax for source annotations remains to be agreed; no new Pyrope syntax is asserted by this example. External metadata makes A/B experiments possible without changing RTL. Use an explicit scope and stable hint ID to replace or disable one inherited hint in a particular instance; do not silently resolve ambiguous names or append conflicting duplicates.

Preserve declaration identity and instance scope across coloring, inlining and mapping. If a memory becomes multiple SRAMs, its logical reference resolves to a group of those SRAMs. If it disappears, report the unresolved hint and skip it. Do not guess a physical target from a coincidentally matching flattened name. The initial example concerns macros; standard-cell references need the same identity and disappearance rules before being supported.

Round-trip intent separately from incremental results

The output bundle preserves the input livehd.placement.hints record, including its relative references and stable IDs. Observed coordinates belong to livehd.placement.state; achieved/relaxed relations belong to livehd.placement.hint_results. Neither is implicitly promoted into user intent. Incremental state may include kind=position hints with exactly the same coordinate fields and validation as authored hints; it remains generated state. Automatic import of this exported state is not enabled yet. An exported relative or coordinate suggestion can reuse the hints payload shape under livehd.placement.suggestions, requiring explicit selection before it influences a future run.

The existing completed-placement cache records netlist, technology, relevant options and consumed-hint identity; the exported coordinate record is an observation, not a self-admitting cache. Changed intent invalidates affected placement reuse; it must not be overwritten by old saved coordinates. Unrelated report changes must not invalidate placement. A single combined metadata file is the placement external interface; separate compact JSON/JSONL workdir shards remain permitted. Packing or splitting preserves record identity and meaning, not a last-writer-wins merge of unrelated JSON objects.

How it guides the stages

  1. FP: resolve the hint graph once and add normalized soft proximity, order and alignment objectives to the relevant groups. Keep ordinary connectivity and density objectives. Do not enable timing feedback in this stage.
  2. Macro planning: refine using physical macro extents, legal orientations, halos and channel requirements. Existing snap/group machinery is a possible implementation aid, but an advisory hint must remain relaxable. Fixed imported positions and legality take precedence.
  3. Final cells: keep the accepted macro frame fixed and run the ordinary final placer. Hints create no circuit edges, timing arcs, buffers, pins, or additional occupied area. Report achieved versus requested relations after macro legalization, not just their temporary GP positions.
