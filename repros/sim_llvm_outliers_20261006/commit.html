Can state updates become contiguous vector copies?

Yes, after changing the state layout, but these experiments found no meaningful simulation speedup. The generated per-register assignments already use SIMD moves. Repacking current and next state into matching contiguous banks permits larger inline copies; reducing commit branches further still failed to improve the complete simulation. No production compiler change was applied from this experiment.

Existing layout and instructions

The user's Z→Y update corresponds to state = state_din in the root __color_commit. Current generated headers interleave each current value with its staged value. In the AXI harness, lfsr occupies offset 16, lfsr_din offset 40, sum offset 64, and sum_din offset 88; each object is 24 bytes. None of the three inspected designs has a matching pair of contiguous multi-register source and destination ranges.

// Original declarations: separate copies are required.
Q0, D0, Q1, D1

// Experimental declarations: both ranges are contiguous.
Q0, Q1, D0, D1
memcpy(&Q0, &D0, sizeof(Q0) + sizeof(Q1));

Replacing each individual assignment with __builtin_memcpy leaves the commit instruction counts unchanged: AXI 105 instructions / 24 vector moves, AXI-Lite 185 / 44, FIFO 228 / 50. The compiler already uses 16-byte SIMD moves, plus an 8-byte move for 24-byte objects. Constant-size copies are inlined; there is no external memcpy call. The following five-repetition batch shows essentially unchanged timings.

Contiguous-bank experiments

Reordering adjacent flop declarations into current-state and next-state banks creates six AXI copy groups of 32–48 bytes covering all 12 scalar states, and seven FIFO groups of 32–64 bytes covering 16 of its 25 scalar states. Actual compiled offsets and trivial-copyability were checked; all generated C++ objects were rebuilt against the modified headers. LLVM kernels retain the same graph, partition and arithmetic. Memory callback inlining is retained in every modified FIFO variant. Memory commits and unbanked scalar commits remain unchanged.

The first experiment copies a group only when every original commit flag is set, otherwise retaining individual updates. It increases static instructions (AXI 105→151, FIFO 228→301) and gave no consistent gain. Subsequent variants seed staged banks from current banks at reset-settle, then use the invariant !commit_flag ⇒ D == Q at the commit barrier. This permits copying inactive members without changing their values. Original flags still control dirty notifications; copying bytes alone cannot replace that bookkeeping.

Counts are static instructions in the root commit function, not dynamic execution totals. The packed-flag variant substantially reduces branch and instruction counts while retaining SIMD copies, yet is slower in the full simulation. These data do not isolate a microarchitectural cause. They do establish that this particular bank-copy transformation is not a demonstrated remedy for the remaining LLVM/Slop gap.

Correctness and scope

288 short executable runs matched checksums across eight variants, two designs, nine cycle counts (0, 1, 2, 3, 7, 31, 127, 997, 10007), and both zero initialization and seed 7 initialization. An instrumented bank-copy variant explicitly checked the inactive-state invariant at every commit for 2 full-length runs: AXI 16,129,032 cycles and FIFO 15,151,515 cycles. All checks passed, including original full-length checksums 1956944815607682736 and 17427903416933715990 respectively.

These are generated-code experiments on specific single-edge flop fixtures. They are not a proof for arbitrary gated clocks, multiple clock edges, latches, memory objects or checkpoint reloads. A production implementation would need layout-defined contiguous banks grouped by compatible commit phase, trivially copyable storage, nonoverlapping ranges, preservation of dirty notifications, and a guaranteed staged-value invariant. A uniform raw array could offer larger groups than these hierarchy-preserving banks, but this experiment does not establish its performance.
