Why the smaller simulations slowed down

The earlier slowdown refers to simulation execution. Native object creation does not inherently make generated arithmetic slower. The previous backend optimized LLVM kernels together with their C++ callers; the independent-object backend retains the call boundary and temporary packing work.

What survives the compilation boundary

  • The generated adapter packs one LFSR value into four differently masked input slots. The separately compiled kernel loads and masks those inputs again. Combined optimization could simplify across that boundary.
  • Adapters initialize temporary arrays, copy old outputs for change detection, call the kernel, then unpack outputs and propagate dirty flags. The old optimizer could scalarize these stack arrays after inlining.
  • A color with no logical output or state effect still makes a call whose entire native body clears an unused changed-word scratch slot and returns.
  • The inspected color-0 object repeatedly stores and reloads a partially accumulated changed-bit word. Accumulating it in SSA and storing once is another concrete optimization candidate.

These are opportunities to remove redundant work while keeping independent objects. A larger improvement would give the LLVM object direct access to shared packed simulator state and move packing, changed-value handling and eventually commits into the object. The controlled experiment above is diagnostic; it does not restore cross-language inlining in the production backend.

Unused Slop .pure.inc arithmetic evaluators are gone for LLVM. Circuit arithmetic and kernel memory operations are inside the independent objects; the kernel no longer calls generated C++ memory wrappers. Shared packed-memory support still handles reset, checkpointing and outer state commits.
