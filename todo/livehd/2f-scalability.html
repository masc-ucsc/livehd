2f-scalability Memory-bounded placement in chunks of 1, 2, 4 or 8 GB

Plan written 2026-11-10. Only step B (memory per cell of the current pass) has started; the chunking itself is not implemented or scheduled.

Cut the floorplan into chunks sized by memory, so that synthesis, timing and placement of a design of any size run on a machine that has a fixed amount of memory for data: 1, 2, 4 or 8 GB per chunk. A fast global placement with no wire RC and no timing gives a stable floorplan. The floorplan is then cut into chunks, and each chunk gets its detail (RC, timing, legalization, repair) on its own, with the rest of the design reduced to fixed points on the chunk edges. Chunks follow the synthesis colors, so that an incremental edit of one color replaces a small part of one or two chunks instead of the whole placement.

Goals

  • Four budgets. The flow takes a data budget of 1, 2, 4 or 8 GB and sizes its chunks to fit. The budget, not the number of colors, decides the number of chunks: a design the size of minion has hundreds of colors and needs only a handful of chunks, each holding dozens of colors.
  • 1 GB is the stress case. It is expected to be too small for good results. It is in the plan to show what is lost when the chunks are pushed too far.
  • 8 GB is the reference. For minion it means one or two chunks, so it is close to a flat run and shows what chunking itself costs.
  • Size independence. A design 100 times larger than minion uses the same budget per chunk and about 100 times more chunks.
  • Parallel later. A chunk depends only on the previous round's fixed points, so chunks can run at the same time, one process each. A machine with M GB runs M / budget chunks at once, which is the practical advantage of the smaller budgets.
  • Incremental. After a small edit of one color, only that color's part of its chunk is placed again. A full redo is needed only when the color grows well beyond the free space around it.

What "data budget" means (proposed)

The peak resident memory of the process that handles one chunk, without the executable and shared-library code: heap, stacks, and the technology data it loads. It is measured with LHD_PHASE_MEM=1 (per phase and per stage) and checked for the whole process tree. The global phase and the stitching steps between rounds must fit the same budget.

Why it is kilobytes per cell: names, not numbers

Checked 2026-11-10 in a second heap dump of the same run (7.2 GB in use). 4.1 GB of it are 28 million heap blocks of about 150 bytes each, 42 per cell, from three places: the copy constructor of View (1.65 GB), make_arrays (1.61 GB) and place_single_frame (0.88 GB). They are copies of instance names and map nodes keyed by them:

  • The placed DEF has 667,612 components with an average name of 108 characters (the full hierarchical path), 664,274 nets and 2,473,583 connections, 3.7 per cell.
  • Endpoint (place.cpp) and physical::Connection are {std::string instance, pin}. Every connection carries its own copy of the 108-character instance name, in each model that lists connections.
  • View holds pins, drivers, nets (std::map<Endpoint, std::vector<Endpoint>>), bus_names, and maps from name to index (cell, terminal, weights, cohesion_owners). Cell has three strings, physical::Component two, physical::Net a name and a vector of connections.
  • View is copied whole (auto snapshot = v and ten similar places), so two or more complete string models are alive at the peak.
  • The flat graph repeats the names as attributes (carry_node_attrs 0.25 GB).

A model of numbers needs a cell index, a type index, a position and an orientation per cell, a net index per pin, and one table of names: a few hundred bytes per cell. The native placer model is already that (about 210 bytes per cell). So the 11.7 KB per cell is not a property of placement; it is the cost of using names as identities inside the pass.

Rule for the rest of step B: no copy of what the graph holds

Ruling 2026-11-11: information is not replicated when it can be avoided, and a table keyed by a string is suspect wherever a graph is in hand. Name and Pin_label keep results identical while the copies shrink; they are not the end state. The end state keys by node and pin ids (or by the index the placer arrays already use), keeps per-node data in dense attributes and per-definition data in class attributes, and reads a name from the graph only where text is written. Where the visiting order comes from names today, the ids are sorted once by the graph's names, so results do not change.

Count of string-keyed containers in sources that have a graph (tests excluded): pass/place 499 (place.cpp 75, repair.cpp 38, resize_engine.cpp 26), pass/lec 200, lhd 195, inou/cgen 87, pass/opentimer 77, pass/synth 53, inou/lefdef 52, pass/domplace 42. In placement they are keyed by cell, net and pin names almost without exception (old, drivers, names, components, positions, net_of_, pin_cap_ and so on).

The replicas that still cost memory in a minion placement, largest first:

  • the placer arrays: two full copies inside every native placement call, the split model and a metrics copy in the boundary refinement, and a saved state from the previous call (DREAMPlace);
  • the flat graph as a second copy of the hierarchy: per node, the full name as a string (the instance prefix plus the name in the definition), about 0.13 GB, and the same names once more in the name table. The color group and the placement block are done (see the table above);
  • the netlist held four times next to the graph: the view's net map with its pin and driver lists, the floorplan's nets, the placer arrays and the RC model, with two name-to-index maps to join them;
  • each cell record copying name, master, block and position out of its node, and the floorplan component copying them again;
  • the control-pin text sets, which are the per-net ignored flags spelled out pin by pin in two text forms;
  • with timing on, the label tables of the timing feedback and of the timer bindings.

  • All of these are with timing off. Timing adds at least the 6 KB per gate of the OpenTimer model, and far more in the current timing-driven loop. The per-cell cost of timing inside a chunk is not known yet and is the largest unknown in this plan (step H).
  • The global phase cannot hold every cell of a very large design: the native model alone is about 210 bytes per cell, 14 GB for 100× minion. It has to place clusters. At that cost a budget holds about 3.5 million movable objects per GB.
  • Even one position per cell (8 bytes) is 0.5 GB for 100× minion, so the state shared between chunks lives on disk, split by chunk, and only a per-chunk summary stays in memory.

Approach

  1. Coarse global placement. No wire RC, no timing, every edge with the same weight. The objects are clusters: colors, or groups of small colors, and macros. This gives one position and one area per cluster and a density map. It is fast and its memory depends on the number of clusters, not on the number of cells. For a design that fits the budget whole, the objects can be the cells themselves.
  2. Cut into chunks. The budget and the measured cost per cell give the number of cells per chunk. The cut lines run between clusters, so most colors land whole in one chunk. A color larger than a chunk spans several. Colors are never split for synthesis because of this: the cut only decides which of a color's cells are loaded together for placement.
  3. Fix the crossing points. Every net that crosses a chunk edge gets a fixed point on that edge, like a pin of a soft macro. A chunk sees its neighbours only through these points.
  4. Detail per chunk. One process loads the chunk's cells and its crossing points, refines the placement with RC and timing, legalizes, repairs, and writes the positions back. Chunks run one after the other, or at the same time.
  5. Rounds. Between rounds the flow updates the crossing points and the boundary timing, and moves area between chunks that are over and under capacity (a small flow problem on the chunk graph). Two tilings alternate, shifted by half a chunk, so that a cell on a boundary in one round is inside a chunk in the next. No cell has a permanent owner.
  6. Global nets. Clock, reset and nets too large to split (the boundary-pin code already leaves nets over 1,000 pins unsplit) stay with the global level. A color that spreads over most chunks is treated the same way.

Storage between rounds

The stored unit is a tile, a quarter of a chunk. A chunk is a group of adjacent tiles, and the shifted tiling is a different grouping of the same tiles. Each tile file holds its cells, positions and the crossing points on its edges. A table maps each color to the tiles it touches. The mapped netlist is already stored per color (one region module <top>__c<color> in the region cache), so a chunk can load its colors without loading the flat design.

Incremental path

  1. The edited color is mapped again. This is per color today: a leaf edit of minion mapped 45 of 457 regions again.
  2. The color's chunks are loaded. Every other color in them is held fixed, and only the edited color, with a small margin around it, is placed from scratch against the fixed crossing points. Old cells are not matched to new ones, because mapping may rename most of them; flops and boundary nets are the stable references.
  3. Escalation:
    • the growth fits in the free space kept in the chunk: done;
    • it does not fit: area moves to the neighbouring chunks and those are redone;
    • the crossing nets changed a lot, or the neighbours are also full: the global phase runs again.

What exists already

  • Colors in the floorplan. The FP stage already moves hierarchy candidates and color leaves as circles with their own area budgets (synth.place.fp.colors, pass/place/color_centroids.cpp).
  • Region mesh. Region_mesh cuts the placed design into rectangles of at most region.max_cells cells with explicit membership and writes region_mesh.json. Minion gets 203 rectangles. A chunk is a group of these.
  • Fixed boundary pins. region.boundarypins cuts each net where it crosses a rectangle edge, joins the pieces through fixed zero-area terminals and writes boundarypins/pins.tsv as the pin contract. Today it builds one model for the whole mesh in one process and removes the pins before legalization.
  • Timing at color ports. 2is-incsynth saves the arrival and required times that each placement stage measured at every color's ports. The same record is what two chunks exchange at a crossing net.
  • Mapping per color with a region cache, and the region cache libraries now released when the pass ends.
  • Measurement. LHD_PHASE_MEM, stage lines in pass.abc and pass.opentimer (core/stage_mem.hpp), and heap profiles by owner (jemalloc).

Facts to confirm first

  • F1 — color locality. In a flat minion placement, cut the die in 2, 4 and 8 and count the pieces each color touches and the nets that cross each cut. If most colors touch one or two pieces the plan holds as written. If not, the coloring needs a locality term before anything else.
  • F2 — memory of the FP stage. How much of the 7.84 GB is already in use while the FP stage runs, and whether that stage loads every cell.
  • F3 — independence of regions today. Whether any region consumer can run on one rectangle without the full design in memory. The boundary-pin model suggests not.
  • F4 — technology data. The footprint of Liberty and LEF once loaded, which every chunk process pays.
  • F5 — memory macros. Why minion with memory macros stops in placement. Until it is fixed, measurements use synth.memory=flops, which inflates the cell count.
  • F6 — cost of timing per cell in the placement loop, on a design small enough to finish.

Steps

  • A — locality measurement (F1). A script over an existing placement and the color table. No change to the flow.
  • B — lower the cost per cell of the current pass. Each of these helps a flat run today and every chunk later.
    • B1: skip wire RC when timing is off (1.39 GB) and remove the in-memory DEF round trip (0.77 GB). That alone takes minion from 11.7 to about 8.5 KB per cell.
    • B2: indices instead of names. Endpoint and Connection become a cell index and a pin index of the cell type; nets become index arrays; names are kept once (or read from the graph when a file is written); a snapshot of a View copies positions only. This removes most of the 4.1 GB of name copies and is the largest single reduction known. The chunk counts in the table above must be computed again after it: minion with timing off may then fit whole in the smaller budgets, which moves the stress case to larger designs.
    • B3: the flat graph (1.2 GB, 1.8 KB per cell), which is then the largest remaining owner.
  • C — budget and estimator. chunk.memory_gb and a predicted peak per chunk from cell, net and pin counts. Every run reports predicted against measured peak. The default keeps one chunk, so results do not change.
  • D — coarse global placement. A mode with equal edge weights, no RC and no timing, on clusters built from colors. Check first how far the FP stage with fp.colors already is this mode.
  • E — chunk cut and tiles. Tiles from the coarse result with cut lines between clusters and at macro edges, the color-to-tile table, and the tile files.
  • F — crossing points as a stored contract. The boundary-pin model applied to tile edges and kept on disk across processes and rounds, with capacity per edge.
  • G — one chunk in one process. Load a chunk from its tiles, refine, legalize, write back. A sequential driver walks all chunks. This is the first point where the peak can be compared with the budget.
  • H — timing per chunk and stitch. Timing inside the chunk with boundary arrival and required times, exchanged between rounds. This shares the work of timing per color in synthesis and depends on F6.
  • I — rounds. Shifted tilings, area transfer between chunks, damping, and a stop rule.
  • J — parallel chunks. One process per chunk, results independent of the order and of the number of processes.
  • K — incremental color replacement. The path above with its escalation, and a test that edits one module of minion and checks which tiles were rewritten.
  • L — synthesis under the same budget. Timing per color with a stitch instead of the flat OpenTimer model, and the one mapping region that needs 730 MB on its own. Color sizes stay as they are unless a natural cut is found: a color is not split only because it is over a cell count.

A and B are useful on their own and can be done at any time. C to G give the first run under a budget with timing off. H to J make it usable. K and L can follow in either order.

Experiments

Each budget (1, 2, 4, 8 GB) against a flat run of the same design, first on minion and then on a larger design. For each run:

  • peak data memory per phase and per chunk, against the budget;
  • number of chunks, nets crossing chunk edges, and colors that span more than two chunks;
  • wire length, worst and total negative slack, and legality, against the flat run;
  • rounds until the stop rule, and wall time sequential and parallel;
  • for the incremental path: tiles rewritten and time after a one-module edit.

Acceptance

  • Minion completes placement at each of the four budgets with the measured peak under the budget, and the report shows predicted against measured peak per chunk.
  • The 8 GB result is within noise of the flat run. The loss at 4, 2 and 1 GB is published, whatever it is.
  • A design that does not fit flat on the test machine completes at 4 GB per chunk.
  • The result does not depend on the number of processes.
  • A one-module edit of minion rewrites only the tiles of the edited color, or reports which escalation it took and why.
  • With chunk.memory_gb=0 every existing result is unchanged.

Risks

  • Quality at the boundaries. Fixed crossing points are a constraint a flat placement does not have. The size of the loss is unknown until the experiments.
  • Colors that do not stay together. Colors come from logic structure, not from location. F1 measures this before any design work.
  • Oscillation between rounds. Shifted tilings help but do not guarantee convergence.
  • Timing memory. If timing cannot be bounded per cell inside a chunk, the 1 and 2 GB budgets may only be reachable with timing off.
  • Macros. They are placed in the global phase and are fixed for every chunk, so a poor macro placement cannot be repaired later.
  • Free space for increments. The space kept in each chunk for growth costs area in every run.
