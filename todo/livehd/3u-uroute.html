3u-uroute Few-shot learned congestion prediction as the third routability rung

Add a learned congestion estimator, modeled on URoute (Lin, Lin, Liu, Du, URoute: Universal Routability Prediction, IEEE TCAD 45(7), July 2026), above RSMT-RUDY in the one-way routability ladder of 3r-route: rudy → rsmt → uroute. The estimator is a small convolutional encoder-decoder with a cross-matching block. It takes the four feature maps the placer can already compute (RUDY, PinRUDY, macro region, cell density) plus a support set of earlier feature/label pairs, and predicts the routed track utilization and DRC density map. Adapting it to a design needs no training: the support set is the adaptation. LiveHD does inference and data export only. An external script, run by the user, reads fully routed OpenROAD results, builds the sample pool, trains the universal weights, and writes both back into a project data directory that LiveHD reads on its next run.

Why

  • RUDY-family estimators are blind where it matters. Both bounding-box RUDY and RSMT-RUDY distribute demand geometrically. Neither knows about pin access, via stacks, layer assignment or detours around macros, which is where routers actually fail. The paper's ablation shows RUDY and PinRUDY are useful inputs, not sufficient predictions. A learned map on top of them is the cheapest step toward router fidelity that does not run a router.
  • Our flow is the paper's premise. URoute was designed for iterative chip design where the same RTL is placed many times with small changes. CNN, Eyeriss and the lhdtrack designs are placed over and over as LiveHD changes. Every routed result is a free labeled sample for the next run of the same or a nearby design. One support sample already matched fully supervised baselines in the paper; five is the default.
  • Cheap at inference. Tens of milliseconds and well under a gigabyte in the paper on a GPU; roughly a second on CPU for a hand-rolled implementation at 256×256 with 64 channels. The ladder samples once every 20 GP iterations and once at convergence, so a second per call is invisible.
  • The slot exists. 3r-route R7 reserved a model-agnostic third rung with its own switch level. This fills it with something cheaper than a global router and leaves grt as a possible fourth rung.

What URoute is (paper facts that bind the design)

  • Problem. A task maps a W×H×4 feature stack to a W×H label map. A task is a (RTL, technology, chip type, metric) combination. The paper uses 256×256 tiles and min-max normalizes features and labels to [0,1] per sample.
  • Features. RUDY (bounding-box, eq. 5–6), PinRUDY (per-pin box density, eq. 7–8), MacroRegion (0/1 per tile, eq. 9), CellDensity (overlap area sum, eq. 10). All four are already computable from the placer's Design snapshot; the first is RudyModel::bbox.
  • Network. Four-level encoder for the query, four-level encoder for each support pair (features and label concatenated on the channel axis), a cross-matching module per level, four-level decoder with fusion, and a 1×1 output conv. Residual conv blocks, ReLU, bilinear up/down sampling, 64 output features per level. Cross matching (eq. 12–14): z = Conv(x ‖ s), u = Σ σ(Conv(Avg(z))) · s, y = ReLU(Conv(u)).
  • Training. Episodic meta-learning with importance sampling over tasks (Algorithm 1): Eq. 15 uses the root mean square of recent task losses and Algorithm 1 mixes in 1% uniform probability. The initial plan's square-root-mean-plus-.01 rule remains the local trainer default; explicit --sampling paper-rms selects the equation/algorithm rule without changing that default. MSE loss; AdamW; rotation/flip/translation augmentation; support size 5. About 17,500 samples from 16 designs, roughly seven GPU hours.
  • Inference. Query features plus N support pairs from the same RTL (or, when none exist, from related designs); no weight update. Robust to which support samples are chosen (std 0.001–0.002 across splits).
  • Reported gains. Five-shot URoute beats task-specific FCN, RouteNet, CircuitGNN, PROS and CircuitFormer on every held-out task, including an unseen technology node. It is never compared against RUDY as a predictor; that comparison is ours to make (U0/U6).

Deterministic, serial, no new Bazel dependency. The architecture is frozen to the paper's shape plus a version tag; a shape change is a coordinated script+C++ change.
U5Where does it act? Ladder rung in final cell GP: rudy → rsmt → uroute, same one-way latch, same consumers (inflation, convergence test). It activates only after the rsmt switch, so inputs resemble converged training data. FP and macro stages get a probe only (one evaluation at the convergence candidate, bounded feedback on failure), the same shape as the existing rsmt probe. Macro channel pressure stays on rsmt.

Feature contract

Features and labels must come from the same geometry, and the in-placer features must be computed exactly as the script computes them. This is the one place where LiveHD and the script share code by definition rather than by library, so it is written down:

  • Grid. A fixed 256×256 tile grid over the core box (the paper's size; the network is fully convolutional, so other sizes work but the pretrained weights assume this scale). The placer's own route bins (bins=64 default, up to 512) are resampled to it by area-weighted binning for input and back for output. The export records both grids.
  • RUDY = RudyModel::bbox without the DREAMPlace pin-count weight and without the obstacle path; PinRUDY per the paper; MacroRegion from physical macro footprints (not halos); CellDensity from physical cell boxes (no fillers, no inflation). Each is min-max normalized per sample, as in the paper, with the raw min/max stored next to the map.
  • Geometry gap. The handoff re-legalizes, CTS adds buffers, repair resizes. The script therefore computes features from the routed DEF (post-CTS placement), not from LiveHD's export, and stores LiveHD's export alongside only for the gap measurement (U0 records the per-sample feature distance). With 3x-reroute's aligned handoff the gap shrinks to CTS buffers.
  • Labels. Horizontal and vertical utilization per tile per routing layer group (M2–M3, M4–M5, upper), collapsed to one max(h,v) map for the paper-shaped task; DRC marker count per tile; per-net detour ratio (routed length / FLUTE length) aggregated per tile. Labels are stored unnormalized with the normalization constants, because the ladder's switch/target levels are absolute (see Calibration). Failed routes are stored with status: unrouted and the last global-route overflow map; they are never silently dropped.
  • Versioning. feature_version, label_version and arch_version in the manifest. LiveHD refuses a directory whose versions it does not implement, with a clear diagnostic, and falls back to rsmt.

Support selection

  1. Same top and technology, newest first, up to uroute.shots (default 5). A floorplan signature (die size, macro set, utilization) orders ties; it does not exclude.
  2. If fewer than uroute.min_shots (default 1) match, fall back to the nearest samples in the pool by L2 distance over the normalized query features of the current placement, same technology preferred.
  3. If the pool is empty or every candidate is version-incompatible, skip the rung for this run and report why. The rsmt behavior is then identical to today's.

Selection is deterministic given the manifest, and the chosen sample ids are written to gp_history.json so a run can be reproduced after the pool grows.

Ladder integration (U5 detail)

  • RudyModel { bbox, rsmt, uroute } and RouteModel { off, rudy, rsmt, uroute, automatic }. In automatic, the final stage latches rudy→rsmt at final.route.switch as today, then rsmt→uroute once final.route.uroute_hold consecutive samples measure an rsmt overflow at or below final.route.uroute_switch. One way; never back.
  • At the uroute switch sample, evaluate rsmt and uroute once each and record both overflows, exactly as the rudy→rsmt switch does, so the scale step is visible.
  • URoute returns the paper-shaped utilization map resampled to the placer's bins as RudyResult::horizontal/vertical (the single-map prediction is split by the rsmt h/v ratio per bin), with pin_utilization from rsmt unchanged. Blocked pins, unroutable nets and detour_wirelength stay from the rsmt measurement; the network does not predict them.
  • Consumers unchanged: inflation (monotone), convergence test on the active model's target. Macro pressure never reads uroute.
  • FP and macro: S.route.probe=uroute extends the existing probe with a model choice. The rsmt probe semantics (one evaluation, bounded continuation on failure) are reused.
  • Cache identity: weights hash, pool manifest hash, selected sample ids, shots, switch level and arch version join the placement cache key next to the route-model key in pass/place/place.cpp.

Calibration

The network predicts normalized utilization; the ladder compares absolute overflow. Two steps keep the thresholds meaningful:

  • Denormalize with the support set. Each support label carries its raw min/max. The prediction is mapped back with the support set's median constants, giving utilization in tracks-per-track units comparable to rsmt's.
  • Overflow definition. RudyResult::overflow keeps its meaning, mean excess over 1. Because routed utilization saturates below 1 where the router detoured, the DRC map is added as a second term: predicted DRC density above uroute.drc_level counts as overflow in that bin. U6 sets the level from the reference data; until then it is 0 and the DRC map is report-only.

  1. U0 — Router reference and baseline (shared with 3r-route R0).

    • Score bbox RUDY and RSMT-RUDY against it: Pearson/Spearman over tiles, SSIM, NRMS and top-5% hotspot overlap. This is the number URoute has to beat.
    • Record the feature gap: distance between features from LiveHD's final placement and from the routed DEF, per design.
  2. U1 — Export from LiveHD.

    • Feature computation shared with the inference path (one function in the DREAMPlace sibling, unit-tested against the Python reference on a fixed small design: byte-equal maps).
  3. U2 — Update script (tools/uroute/, Python + PyTorch).

    • export: PyTorch state dict → flat weight file with the header LiveHD reads; round-trip test loads it back and compares outputs.

Facts to confirm first

  • Whether the authors released code or weights (the paper names none); if yes, U2's network must match it layer for layer so their weights are a valid starting point.
  • Exact block details the paper leaves implicit: residual block depth, where downsampling happens, fusion operator in the decoder, channel count of the cross-matching convs. U2 fixes them and records them under arch_version.
  • How OpenROAD exposes per-GCell utilization after detailed route (odb wire iteration versus report_wire_length versus the 5_1_grt congestion map). The extractor should not depend on the global-route report alone (U2 ruling).
  • Whether 256×256 is a sensible tile size for our dies: CNN and Eyeriss on asap7 are far smaller than CircuitNet's designs, so a tile may be a handful of sites. Measure the tile size in sites and tracks and record it in the sample.
  • Thread safety is not an issue (serial by ruling), but FLUTE/rsmt still run at every uroute sample for pin, blocked and detour terms. Measure the combined call time.

Risks

  • Distribution shift. Training on converged routed layouts, inference during GP. U5 limits exposure to the post-rsmt tail; if U6 shows the prediction degrades on unconverged inputs, retreat to probe-only (the option surface already allows it).
  • Few designs. A user's pool will have a handful of designs for a long time. The nearest-design fallback and the shipped weights are the mitigation; the skip path is the guarantee that nothing gets worse than today.
  • Contract drift. Feature code exists twice (C++ and Python). The byte-equal unit test in U1 and the golden test in U3 are mandatory, not optional.
  • Small dies. See the tile-size fact above; a too-coarse or too-fine grid makes the pretrained weights meaningless.

Cost

  • Inference: one forward pass per sample, roughly 20–50 GFLOP for five shots at 256×256 with 64 channels; about one second single-threaded with a decent inner loop. Sampling cadence makes this negligible against GP time.
  • Training: minutes on CPU for a pool of tens of samples when fine-tuning from the shipped weights; hours on GPU for a from-scratch universal model.
  • Storage: a sample is 4+3 maps at 256×256 f32, about 1.8 MB; f16 halves it.
