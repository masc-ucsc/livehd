json-metadata One composable metadata file across passes

Audit and design proposal, 2026-10-27. LiveHD should identify each JSON entry by its class, preserve user intent alongside generated results, and accept the same metadata whether supplied in one combined file or stored in separate workdir shards. The current readers do not yet support that uniformly.

CLI input cleanup: pass one or more JSON paths beside the design inputs, for example lhd synth top.v intent.json tuning.json --top top. Combining their arrays into one file is equivalent. livehd.placement.hints, livehd.synth.tuning, and livehd.sim.tuning select their consumers; livehd.physical.row_access supplies a strict convention object for domino generation. Unrelated classes are retained. Conflicting record identities are rejected. The removed synth.metadata, synth.tune.file, sim.tune.file, and synth.place.row_access options produce a migration diagnostic. Tuning export paths remain outputs, and private workdir caches retain validation gates. Generic attribute-loader file labels, external JSON protocols, query arguments, and JSON design formats are not tuning-file selection options.

Record presence activates that consumer's metadata, not an unrelated pipeline stage: placement hints do not turn synthesis-only runs into placement runs, and row-access records do not select the domino mapper. Tuning exports consolidate the consumed tuning section and retain unrelated records and other design scopes. Internal validated trial files and workdir cache shards remain implementation details. Inline JSON value options such as per-color region_opts are not file selectors and are unchanged.

Depends on

No new placement algorithm is needed for the shared transport. The hierarchical placement-hint sketch uses positional JSON inputs. Synthesis and simulation tuning also select class-tagged records; source attributes and internal cache schema migrations remain pending.

Design notes: findings

Tests, contract files and benchmark/script subdirectories were excluded from that production-oriented scan. Some matches are internal strings, tools or protocol payloads rather than metadata files. This is a coverage inventory, not a claim that every payload has been semantically validated. Each migration needs its producer/consumer pair audited. Proposed common shape

Use an array of typed records, extending the existing attribute IO convention. A single-record file is a one-element array; combining files combines records, not object fields. Each record has class, integer schema_version, stable id, and design scope. Design-independent records use an explicit null design. Identity is the tuple (class, design, id). Template/module/instance selectors live in the class payload. Per-class versions evolve independently; no whole-tool format version is needed.

[
  {"class":"livehd.placement.hints","schema_version":1,
   "id":"floorplan-intent","design":"chip.top",
   "templates":[{"module":"bank","hints":[
     {"id":"pair","kind":"snap","subject":"data","relative_to":"tag","side":"east"}
   ]}]},
  {"class":"livehd.placement.state","schema_version":1,
   "id":"macro_plan","design":"chip.top",
   "depends_on":[{"class":"livehd.placement.hints","design":"chip.top",
                  "id":"floorplan-intent","digest":"sha256:EXAMPLE"}],
   "netlist_digest":"sha256:EXAMPLE","technology_digest":"sha256:EXAMPLE",
   "options_digest":"sha256:EXAMPLE","code_salt":"EXAMPLE",
   "hints":[{"id":"data-start","kind":"position","subject":["bank0","data"],
             "frame":"floorplan","anchor":"lower_left","x_um":120,"y_um":80,"orientation":"N"}]},
  {"class":"livehd.placement.hint_results","schema_version":1,
   "id":"macro_plan","design":"chip.top",
   "results":[{"hint":"floorplan-intent","template":"bank","instance":["bank0"],
               "hint_id":"pair","status":"relaxed","reason":"routing_clearance"}]}
]

Illustrative payloads and coordinates only, not a measured run or supported input yet. The digest placeholders are deliberately not valid cache keys. A complete reusable state needs the producer's full dependency descriptor; the abbreviated example is not an admission algorithm.

  • Dispatch on class. Validate the version and payload only with that class's reader. Unknown classes remain uninterpreted and survive export. Unknown versions are preserved but not applied; optional cache state becomes a miss. An incompatible required input gets a diagnostic instead of guessed semantics.
  • Preserve authored hints semantically, including relative references, IDs, types and unknown extension fields. Generated results and state have their own classes. Never replace a relative hint with a measured absolute position.
  • Generated relative or coordinate suggestions may use the same templates/hints payload under livehd.placement.suggestions. They influence a later run only when explicitly selected/promoted. Record the producing run and consumed inputs.
  • Do not use array order as precedence. Identical duplicate identities may be deduplicated; conflicting duplicates get diagnostics, with advisory records skipped rather than silently overwritten. An intentional scoped override must identify the target hint. Reject duplicate JSON object keys during validation.
  • Resolve logical hierarchy using stable definition and instance identities. Use path-segment arrays for generated instance paths to avoid slash/dot escaping ambiguity; display paths are labels, not binding keys. Preserve source-to-physical mapping for split memories and generated synthesis wrappers.

Coordinate hints are advisory too

Accept optional kind=position hints from the user and from incremental output. Use the same payload in both: stable hint ID, subject instance path, explicit frame and anchor, x_um, y_um, and optional orientation. Coordinates refer to the lower-left corner of the oriented physical body before halos, in DEF's global coordinate system; they are not implicitly offset by the core origin. Relative relationships remain the preferred portable form. See the synthetic coordinate example.

Coordinates are movable initial guesses, never fixed constraints. Generated state can retain these hints under livehd.placement.state with its usual dependency/admission information. This shares the coordinate representation without overwriting the authored livehd.placement.hints record or silently promoting all generated state to user intent. After warm-start admission, the same geometric validation applies to authored and generated coordinates.

If a hint cannot be used (overlap with fixed geometry or conflicting coordinate hints, out of bounds, illegal row/site/orientation, unresolved or ambiguous target), discard it and continue ordinary placement. Validate coordinate requests together; file order is not precedence, and transient GP overlap is not grounds to reject every movable-cell seed. A split logical memory needs an explicit group transform, not identical positions for all generated SRAMs.

Report the discarded hint through the standard diagnostic sink at warning severity, honoring --diag-fmt. Include design/instance, record/hint ID, requested pose and reason, with source location when available. Deduplicate the same rejection across iterations. Normal optimization movement of an accepted initial guess is allowed and does not need a warning. An advisory failure must not become a fatal placement error; ordinary physical legality checks still apply.

Style, compactness and storage

  • Use snake_case keys, real JSON numbers/booleans/arrays, integer versions, and explicit unit suffixes such as delay_ps, x_um and area_um2. Missing measurements are null, not zero, NaN, infinity or an undocumented negative sentinel. Keep class-specific absence semantics explicit.
  • Emit compact UTF-8 JSON with one terminating newline. Pretty output is a view for documentation or inspection. Stable field/record ordering makes diffs and hashes reproducible; preserve array ordering wherever it has meaning.
  • Canonicalize consumed records for cache keys so whitespace/object-member order does not invalidate reuse. Specify numeric normalization; preserve integers without a double round trip. Serialize digests as algorithm-tagged strings, not large JSON numbers that external tools could round.
  • Keep one logical metadata input/export at the driver. A registry indexes records once; passes request their classes and scopes. A bundle supports all owned JSON metadata, but does not implicitly embed RTL, LEF, libraries or binary graph snapshots.
  • Workdir sharding is explicitly supported. A shard contains the same typed records; long histories may use one typed record per JSONL line with explicit run/sequence identity. Pack/export produces a single JSON array and import may repartition it. Large artifacts and optional caches can stay separate; missing cache assets cause a miss, not a change to declared intent.
  • Publish per-pass shards atomically; merge/export through one coordinator or locked generation, never competing read-modify-write updates to the same bundle. Do not rewrite the user's input file merely because a pass produced new state.

Incremental reuse without interference

The existing compile semantic/interface hashes, ABC salts, timing-engine identities, proof levels and physical artifact inventories are useful. Preserve those checks and add hashes of the exact metadata records each stage consumes. Hashing the whole combined file would make an appended report invalidate unrelated compile/synthesis caches, defeating the purpose.

  • A changed placement hint invalidates dependent FP/macro/final placement state. It must not authorize stale fixed coordinates. Compilation/mapping can be reused when their own semantic inputs and dependencies are unchanged; the implementation must track placement attributes separately where current fingerprints combine them.
  • A changed timing target/environment invalidates the corresponding timing and repair decisions. A saved mapping or timing observation is not authoritative merely because it is in the same file as a current user hint.
  • Full output reuse requires all current cache-admission checks. A weaker warm start may reuse compatible positions as movable initial guesses, with separate admission and diagnostics. It must never silently turn a hint into a FIXED object.
  • Output retains the original relative-placement record and writes updated state beside it. A stale state record can be discarded without losing the user's intent.

Acceptance before claiming one-file support

Feed the same records as one bundle and as shards through actual pass readers; compare normalized consumed records, deterministic results for a frozen seed, and cache decisions. Round-trip authored hints unchanged while replacing only the producer-owned state/results. Test mixed unknown classes, repeated designs and instances, name escaping, version mismatches, duplicates and stale dependencies. Test valid and unusable coordinate hints from both authored and incremental records, including warning output in human and machine diagnostic formats. Appending a report must preserve cache hits; changing a consumed hint must cause the appropriate miss. Cold and warm runs must retain netlist identity and physical legality. Keep protocol-specific and immutable contract tests intact.
