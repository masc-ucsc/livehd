2i-interact Interactive placement: lhd synth --gui

lhd synth --gui ... runs the normal synthesis and placement flow, keeps the process alive, and serves a browser page that shows the floorplan while the placer works: macros as boxes, cells as dots, optional centroids and map overlays, a crude side panel with stats and controls. The user can pause before any stage, drag or align cells, macros and centroids, and watch global placement (GP) and the stats react. Every action is written to a trace that replays in batch, which is also how video is produced and how an agent will later drive the same controls.

Implemented (opened 2026-11-09) G0-G12 are implemented (see Implementation status). The rulings below came from the user. The design was checked against the code on 2026-11-09 by reading only (Facts checked); what reading could not settle is listed under Still to measure.

Depends on

Nothing outstanding. It builds on the in-process native DREAMPlace (dp::place(Design&, const Options&, GpState*)), its existing per-iteration callbacks, Placement_session (GP stop and resume with GpState), the ECO windowed local_place(), Region_mesh (3g-partitions) and the placed STA callbacks (Physical_session::evaluate).

Why

  • Feedback. Today the only way to ask "what if this SRAM sat in that corner" is a hint file and a full rerun. Moving it with the mouse and reading WNS/TNS/HPWL a few seconds later is a much shorter loop.
  • Visibility. Watching FP, macro GP, final GP and legalization as they run is the cheapest way to see what the tool is doing; today that needs snapshots plus offline matplotlib scripts.
  • Agent control. The same command set, plus a screenshot and a state query, lets an agent look at a placement and act on it.

Rulings (decided 2026-11-09)

  1. Browser front end. lhd serves a local port and opens the default browser; one self-contained page. No native GUI toolkit. Works on macOS and Linux, and over an SSH port forward.
  2. Live for the whole flow. The page shows the placement as every stage iterates. The placer checks for user commands every few GP iterations (1 to 20) and applies them while it runs.
  3. Stage switches are breakpoints. The panel lists the flow parts (FP plan, macro plan, final, legalize, ...), initialized from the options (all the defaults on). A part that is off makes the flow stop before it; turning it on lets the flow continue.
  4. Centroids. An overlay shows the FP/macro-plan centroids; they can be dragged like any object to see the impact.
  5. Pins. A dropped cell, macro or centroid stays pinned at the drop location until the user unpins it. Pins survive into later stages.
  6. Mouse. Click and drag moves an object. Shift+click builds a multi-selection, which can be aligned and distributed as in Inkscape (left, center, right, top, middle, bottom, equal gaps, rows by columns matrix). Aligned objects end pinned.
  7. Pause and run only. One pause/run control, no separate step button. The session starts paused, so the user can set the view and the stage switches first. While paused, edits only accumulate; run applies them all. When the GP of the current stage has already finished, run forces at least 20 more GP iterations (it then stops again on the normal criteria), either to absorb the edits or just to see what more iterations do.
  8. Timing at two rates. Positions and cheap stats (HPWL, overflow, RUDY) go out at every poll. WNS/TNS and the worst path refresh on a slower cadence bounded by a time budget (default 10% of wall time), and always after a released edit and at each stage boundary. Each number shows the iteration it came from.
  9. Action trace. Every action is appended to a trace with the stage and iteration where it was applied. The trace replays in batch with no browser.
  10. Capture. The page has a screenshot button only. Video comes from replaying a trace headless.
  11. Agent later. After the GUI works, an agent gets the same controls (commands, state query, screenshot).
  12. Small footprint on the flow. The existing placement code should change little. After legalization an edit triggers a few GP iterations plus legalization again, scoped to the region that holds the object. A drag that leaves its region regenerates every region.

Threads

The flow keeps its single placement thread. The server thread only parses requests, pushes commands into a mutex-protected queue and serves the last published frame. A paused flow is the flow thread blocked inside a Gui_session call waiting on the queue, so "pause" needs no change to the solver's control flow. The flow never waits on the browser: with no client connected, publishing a frame is a pointer swap.

Protocol (HTTP only, no WebSocket)

GET /stats?since=NJSON, long poll: stage, iteration, run state, HPWL, overflow, route overflow, area and utilization, WNS/TNS with their source iteration, stage switch state, pending edit count.

The server binds 127.0.0.1 and the URL carries a random per-run token; requests without it are refused. A command channel that can move the placement and write files must not be reachable from the network by default.

GP hook

DREAMPlace gets one new callback, Options::interact, called every interact_interval iterations at the site of the existing movable_update. It receives read-only views of the solver's current positions and the iteration, and returns holds (node, x, y), releases, centroid targets and macro pulls. Gui_session implements it: publish a frame, drain the queue, block while paused.

Most of the mechanism already exists and is reused, not rebuilt:

  • Holds exist. The solver keeps movable_holds and a can_move(i) mask applied in the Nesterov look-ahead and in the gradient step; the code states "a hold changes only motion, never net forces or density accounting". A pin is a hold that does not expire.
  • What must be added. (1) Holds on macros: movable_update rejects them with a require. (2) Permanent holds: today a hold is a countdown (fix_iterations). (3) A cheap snapshot: movable_update copies the whole Design (netlist included) per call; interact passes position spans.
  • An edit restarts the optimizer globally. Applying a moved position sets the Nesterov counter to 1, copies prev = x and clears the convergence samples and the best-feasible iterate. This is kept: a user edit changes the problem. During a drag the restart happens at each poll that carries a new position, so the surrounding cells react with gradient steps and regain momentum after the release.
  • The hook must be invisible until the first edit. Merely setting movable_update or macro_pull_update today disables several behaviors (allow_density_floor, the post-density continuation, the routing-plateau handoff, gp_search, checkpoint_rollback). If interact were treated the same way, opening the GUI would change the result with no edit. Those conditions must test "an interactive edit has been applied in this solve", not "the hook is installed".

At the stage boundary the holds become real FIXED status: the macro pass already marks hard macros FIXED and writes macro/fixed.def before the final pass (place_requested), and FIXED standard cells are kept by that hand-off and treated as obstacles by the ECO placer. A pinned cell's drop position is snapped to a row and site when it becomes FIXED.

Pause, and run after GP has finished

  • Pause blocks inside the callback. It must not end the dp::place call and continue with a GpState: a continued solve (state != nullptr) disables the density floor and the post-density and routing-plateau stops, so a GP cut into slices is not the same GP. Blocking leaves the solve untouched. Deadlines in the loop are iteration counts; the clocks only feed the reported seconds.
  • Run after the stage's GP stopped uses what exists for exactly this: Options::min_slice_iterations "requires that many additional steps in the current call, independently of the accumulated GP clock and old convergence deadline", wrapped by Placement_session::advance(..., minimum_steps). The continuation keeps the iteration clock, the density weight and the filler positions. A fixed macro moved while GP is stopped goes through GpRebind::allow_fixed_macro_move, which exists for the macro-plan hand-off.
  • Where GP can be continued. The final pass already runs on a Placement_session. The FP and macro GP are plain dp::place calls inside place_single_frame; continuing them needs their GpState kept and the stage-end work (centroid snap, macro legalization) run again after the extra iterations. See G2.

Stages and breakpoints

The panel shows one switch per flow part, in order, taken from the code's own stages rather than new ones:

Panel nameCodeEdits allowed
fp planPlacement_stage::floorplan, FP GP and centroid snap in place_single_framecentroids, macros, cells
macro planPlacement_stage::macrocentroid targets, macros, cells
finalPlacement_stage::final, run_main_gp cells; macros are FIXED here unless unpinned (see G6)
legalize, detailednative or terminal legalization, detailed placement, legroute when enabledregion-scoped edits after it completes
timing_driven, resize, repair, resynth, satlegalize, final_legalize, preroute post-placement steps in lhd_kernel_synth.cppview only while running

Gates use hooks that exist:

  • Between fp, macro and final: Options::after_stage(Placement_stage, const Result&) is already called after the floorplan GP and after the macro and final passes, and lhd_kernel_synth.cpp already installs it. Blocking there is "stop before the next stage" with no new code in place.cpp. Its boolean return throws Placement_restart for the completed stage, which is a ready-made way to redo a stage from its seed.
  • Before legalization and detailed placement: these run inside the same dp::place call as GP (o.legalize, o.detailed_place). The gate blocks in the existing before_legalize callback and in the observer stage events (legalization, detailed_placement, finished).
  • Post-placement steps: one gui.gate() call between the steps in lhd_kernel_synth.cpp.

Initial switch state comes from the options: a part the options disable (place.final=false, place.fp=false, ...) starts off, and turning it on at the gate runs it. A part can be enabled late, but a part that already ran cannot be undone in this plan.

Centroids

  • FP stage. The centroids are dp::CentroidGroup candidates (hierarchy and color) attracted to their own moving centroid. Design::centroid_targets gives frozen targets but is all or nothing (one per candidate, empty keeps the moving attraction). Dragging one centroid needs a per-candidate optional target, a small DREAMPlace addition carried by the interact return.
  • Macro stage. After the snap the frozen centroid_targets anchor macro GP; a drag rewrites one entry. Macros also have MacroPull (absolute center target with a weight, replaceable mid-run through macro_pull_update), which is the soft alternative to a hold if a hard hold on a large macro turns out unstable.

The overlay draws each centroid with its name and, optionally, lines to its members.

Edits after legalization

The default legalizer works on the whole design; only legroute works per region. So "redo this region" is the ECO placer local_place() with the region rectangle as its window. local_place() today takes a reference floorplan and a list of forced cell names, builds its window as the hull of the changed cells plus a margin that doubles per attempt up to the whole core, locks every cell outside the window, and runs at most 60 GP iterations on 16 bins followed by legalization and detailed placement. FIXED and LOCKED cells are obstacles. A Region_mesh region is a single rectangle with a member list, and rect_of(x, y) already finds the region of a point.

A move on a legal placement then:

  1. finds the region of the old and of the new position of every moved node;
  2. if all stay inside their region: calls local_place() with the current legal floorplan as reference, the moved cells as forced and FIXED at the snapped drop site, and the region rectangle as the first window (a small change: the first window is given, not derived). If the region alone cannot be made legal the existing window growth applies and the GUI reports that the edit spilled;
  3. if any node crossed a region edge: rebuilds the mesh and reruns the region stage for all regions;
  4. refreshes timing and publishes.

The pending edits applied by one run are grouped by region, so each touched region is redone once. The mesh is built in the detail-final phase; it has to be kept in memory after the flow moves on (today it is written to region_mesh.json).

Timing refresh

There is a precedent for a read-only look at a running GP: Options::gp_observer ("diagnostic-only, synchronous observation; never supplies optimizer feedback") samples routing during the final GP. The GUI refresh has the same contract: estimate_rc on the current positions, then Physical_session::evaluate(graph, rc, exclusions, Purpose::ranking), and never refresh_timing_weights or a GpUpdate. Gui_session measures each refresh and schedules the next so that refresh time stays under the budget.

The STA session is stateful (incremental, with a "last evaluated state"), so an extra evaluation between two of the flow's own checkpoints may not be bit-neutral for the next one. Reading the code cannot settle this. Two consequences: timing refreshes are recorded in the trace, so a replay performs the same evaluations at the same iterations and reproduces the interactive run exactly; and whether a GUI run with no edits equals a batch run bit for bit is a test in G6, with "equal QoR within noise" as the fallback claim.

Trace and replay

<workdir>/synth/place/gui_trace.jsonl: one line per applied command, {seq, stage, pass, iter, cmd, args}. Recorded are released moves, unpins, centroid changes, stage switches, run, pause, finish and timing refreshes; intermediate drag positions, view changes and map toggles are not. In replay the same interact hook reads the next line and applies it when the stage and iteration match, so no browser or socket is involved. A pause in the trace is replayed as its recorded iteration count, not as wall time.

Rendering and capture

  • Page. Pan and zoom; macros as outlined boxes with names when large enough; cells as points colored by synthesis color, by region or by slack; pins marked; selection highlighted. Layers: centroids, regions, worst path, density, RUDY, RSMT congestion, URoute congestion, displacement since the last frame (how the other cells moved).
  • Screenshot button. Saves the canvas as shown.
  • Rasterizer. Same layers, simpler look. Feeds /screenshot.png, the screenshot command, and replay video: one PNG per published frame piped to ffmpeg when it is on the PATH, otherwise a numbered PNG directory.
  • Large designs. Above a node budget the frame carries a density raster plus the dots inside the current viewport only.

Agent channel (added 2026-11-10)

A local assistant or script can talk to the open session without a browser and without the token: a Unix-domain socket (mode 0600, announced on stderr and in <workdir>/synth/place/gui_agent.json) serves the HTTP routes plus POST /agent; tools/lhd_gui is the stdlib client. Commands: find, highlight / highlight_names / clear_highlight / highlights (painted in the page, listed in the side panel), critical (worst-slack cells through the ranking timer, served by the flow thread at its next poll or gate), select / selection / describe (the page posts what the user clicks; details include master, LEF class, size and position in um, pins), state and cmd (any page command). Highlights and the selection are session state keyed by node name, so they survive phase changes. Tests: gui_session_test (find/highlight/select/describe, critical answered by a flow thread, the Unix socket and its mode, the TCP side still refusing without a token) and lhd_gui_register_smoke (the same on a real placement through tools/lhd_gui).

Options panel and faster timeline (added 2026-11-10)

The Options panel lists the same entries as lhd list options synth.place (deprecated spellings left out, synth.place and source-attribute entries read-only), editable and grouped, with Rerun from start and Rerun from checkpoint (both re-execute the process; the token and port are kept). lhd_gui_timeline_smoke checks the panel's list equals lhd list options synth.place and a from-start rerun with an edited option. The timeline records every synth.place.gui.history_every (default 50) GP iterations plus every gate/checkpoint, serves the stored 16-bit frames directly, and the page caches and prefetches them (scrubbing 13 snapshots: 25 ms cold, under 1 ms cached); the slider no longer fights a drag and the markers are rebuilt only when the history changes. A from-start restart used to come back with a new token (403 for the open page): fixed.

Failures and keys (added 2026-11-10)

A run that fails after the session started (a forgotten --top, a bad SDC, ...) no longer leaves the page waiting on a dead server: the process stays up, the page shows the error text and hint in a red banner, and Restart (edited flags) re-runs from the start with the flags edited in the panel; Exit lhd ends the process with the failure's exit code (lhd_gui_failure_smoke). The page zooms with z / Z (shift+z) around the pointer, in addition to the wheel.

Still to measure (G0)

  • STA neutrality. Whether an extra evaluate(ranking) between two flow checkpoints changes the next checkpoint's numbers, and what one refresh costs on sha3 and on a large design.
  • Macro holds. Stability of a permanently held large macro under the density preconditioner, against MacroPull with a high weight.
  • FP and macro continuation. What the centroid snap and macro legalization do when run a second time after extra iterations.
  • Fixed off-grid cells. Whether the legalizers accept a FIXED standard cell only on a legal site (the plan snaps it; confirm the checks).
  • Frame cost. Copy and quantize positions at poll=1 on sha3 and on a 1M-cell design.

DREAMPlace workflow (ruled 2026-11-09)

The fork lives at ../DREAMPlace; first fast-forward it to the pinned commit (it is 4 commits behind). While this task is being developed, MODULE.bazel uses local_repository(name = "dreamplace", path = "../DREAMPlace") in place of the git pin. When the work is done and ready to push: commit and push DREAMPlace, then restore the git pin in MODULE.bazel at the new commit and push LiveHD.

Files

  • lhd/lhd_options.cpp, lhd/lhd.hpp, lhd/lhd_meta.cpp: --gui flags, option rows, describe text.
  • lhd/lhd_kernel_synth.cpp: session creation, option reading, gates between post-placement steps.
  • pass/place/gui/ (new): gui_session.hpp/.cpp, gui_server.cpp, gui_render.cpp, gui_trace.cpp, page.html, tests.
  • pass/place/place.hpp, pass/place/place.cpp: observer chaining, interact wiring, gates, hold to FIXED conversion, region-scoped edit entry.
  • pass/place/region_mesh.hpp: lookup of a region by position and by node.
  • ../DREAMPlace/dreamplace/native/placement.hpp/.cpp: Options::interact, holds.
  • pass/place/README.md, docs/placer.html.

Risks

  • Result drift with the GUI open. A run with --gui and no edits must equal a batch run. The read-only timing refresh and the no-wall-time rule exist for this; G2 tests it.
  • Holds versus real fixed objects. A held macro still counts as movable charge, so density near it differs slightly from a FIXED macro until the stage boundary. Fallbacks, in order: MacroPull with a high weight; a rebind with the node fixed when the drag is released.
  • Global optimizer restart per edit. Each applied move resets momentum and the convergence samples for the whole design. On a large design a long drag at a short poll interval could keep GP from making progress; the page then sends drag positions at a lower rate.
  • The 9300-line stage function. Gates and hooks must stay a few lines each; any restructuring of place_single_frame is out of scope.
  • Region-scoped redo. No code re-places one region by id today; boundary pins and bus order live on region edges and may need a refresh when a region's content moves.
  • Hand-written HTTP. Small, but it is new network code; keep it to localhost, a token, fixed-size request limits and no file serving.
  • Two renderers. The page and the rasterizer will differ in look; the contract is same layers and same geometry, not same pixels.
  • Large designs. Full-position frames stop being practical past a few million nodes; G11 is required before those are usable.

Out of scope for now

  • Undo or rewind to an earlier stage (rerun with an edited trace instead).
  • Editing nets, cells or constraints; only positions, pins and centroids move.
  • Routing display beyond the congestion maps.
  • Several simultaneous clients editing; extra clients are viewers.
