2r-refilean Prove refinement across Pyrope rewrites

Let a designer change the latency or internal schedule of a Pyrope design while preserving its observable behavior. Check the original and rewritten Pyrope against the same event specification in simulation and with LiveHD’s Lean refinement checker.

Depends on

None. Build on the existing Lean proof tools and refinement-map format.

Subtasks — pending

  • A — Define what a caller can observe.
    • Describe when a transfer fires, which payload fields are meaningful, and which order the interface promises. Define reset, simultaneous events, and environment obligations. For a ready/valid output, record a word when both signals are asserted. Preserve any cycle deadline that is part of the interface.
    • Use one event description for the simulation scoreboard and Lean channel/slot definitions. Each version binds its own signal names to that description. Keep internal state maps and progress measures specific to each implementation.
  • B — Exercise a latency-changing rewrite.
    • Use a one-entry elastic queue as the first pair. Delay output availability by one cycle while preserving capacity, ordering and backpressure. Drive each version with the same transaction sequence, holding each input until its own handshake. Include reset, consecutive transfers, a stalled sink and a subsequent drain.
    • Compare accepted and delivered words in order. Record the first divergent transaction with its cycle on each side, payload and replayable stimulus. Keep cycle-exact LEC against the previous Pyrope for earlier cleanup steps that preserve timing.
  • C — Prove that the two Pyrope versions realize the same event streams.
    • Export both versions as LiveHD certificates. Start with a common finite specification expressed in registers, which fits the checker’s memory-free specification restriction. Check its channel facts with sym_refmap specfacts. For each version provide the state map, reset base and any needed invariants, prove its obligations with sym_refmap refmap, and compose the checked results. A cycle with no transfer may leave the abstract state unchanged.
    • Check progress separately. For the queue, state the sink fairness assumption explicitly and require an accepted word to be delivered when the sink continues to offer service. Record assumptions, reset scope, progress obligations and the emitted Lean theorem with the result.
  • D — Test the checker with broken rewrites.
    • The latency-only rewrite should pass. A duplicate or corrupted output must fail the event check. A variant that accepts a word and then withholds it forever must fail the progress obligation under the same fairness assumption. Treat a simulation match, an inconclusive proof and a checked theorem as distinct outcomes.
    • After the queue, try a retimed pipeline with backpressure, then an accelerator command/completion interface. For CPUs, define retirement and architectural memory effects explicitly, including the order of multiple retires from one hart. State the allowed cross-hart ordering before comparing runs.
